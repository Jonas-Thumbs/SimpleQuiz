## 6. Retrospective Analysis

### 6.1 Key Learnings

We learned how to build a web-app with a server backend in a team of six developers. This involved learning how to use FastAPI and React, but also included management of the team itself, conducting a proper reviewing process before merging any code, and writing meaningful automated tests.

In this context, our team learned how Selenium can be used to automate testing in a real web browser. We created a simple test that opens the SimpleQuiz homepage, locates the main heading, and verifies that it displays the expected text. This helped us understand the basic Selenium workflow. We also learned that acceptance tests can verify the application from a user’s perspective, while our existing Vitest tests focus on individual React components.

### 6.2 Challenges Overcome

Initially, we planned to have two different types of accounts: One for users and one for teachers. One challenge with this approach was to come up with a developer- and user-friendly way to implement this. In the end, we decided to implement only one account type. All users can now create and take quizzes, so there is no strict distinction between teachers and students.

Also, it was not easy to implement and merge all the user stories in the right order. A story might be delayed because some code it depends on is not ready yet. And some stories turned out to depend on each other, so we had to implement them jointly. For example, the "log in" story can't really be tested repeatedly without "log out" functionality, and vice-versa. Sometimes, implementing a new user story required significant changes to the code of those that were already implemented. One good example of such a case is "assigning quizzes to classes".

### 6.3 Future Improvements

One reoccuring problem was that we tend to do most of the work on a deliverable just before the deadline. This might have led to rushed decisions, which might have contributed to a small number of avoidable mistakes, like not detecting a bug in a pull request. If we were to continue working on the project, we should definitely enforce a stricter time schedule.

Discord proved to be a very effective tool for communicating about problems in the code as well as progress on the various weekly tasks. We will definitely keep this as our main channel of communication.

GitHub issues can be helpful when assigning tasks or monitoring which tasks are yet to be completed. But sometimes, they got outdated when merging or splitting user stories, or we simply forgot to close them. Since this is very confusing, we should make sure to check and discuss the currently open issues in each weekly group meeting.

An optional, but useful to our process would be to add the automated tests to a GitHub Actions workflow so it runs automatically when changes are submitted. This reduces the workload for reviewers while reducing the chance for human error.
